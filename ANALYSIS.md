## 2. How Records works

### Stored state and derived records

Agent's **Records** treatment uses `Ledger`, which owns an ordinary conversation, persisted judge answers, lookup-derived identities, request/annotation bookkeeping, and a usage gauge. A `LedgerRecord` is a **derived projection**, not a separately maintained prose summary: it has a key, title, member identities, and lines retaining source message, sentence, party, topics, and role. The projection also tracks stale material and orphans. ### One response

`respond` rejects overlapping requests with `CONCURRENCY`, calibrates if needed, appends the request, and runs an agent pass. Before generation, selection files missing judgments and builds the briefing/tail. A selection fault falls back to the conversation view. Successful tool results are filed as facts; failed results, tool-calling assistant turns, annotations, and later assistant replies are assigned chatter. [Ledger.ts:270](src/core/ledgers/Ledger.ts#L270) [Ledger.ts:418](src/core/ledgers/Ledger.ts#L418) [Ledger.ts:542](src/core/ledgers/Ledger.ts#L542)

The selected tail has a consequential boundary: `#tail` takes its seed from messages **before the first recorded request**, then chooses fitting complete exchanges from that seed and appends the current request. It is not a moving tail of every intervening request/reply. The later replies' chatter classification also excludes them from ordinary topical recall. The code establishes those selection rules; the size of their task-quality effect remains experimental. [Ledger.ts:889](src/core/ledgers/Ledger.ts#L889) [Ledger.ts:418](src/core/ledgers/Ledger.ts#L418) [Ledger.ts:1025](src/core/ledgers/Ledger.ts#L1025)

The agent observes tool results and stops repeated requests. A partial or blank first pass, unless the caller aborted, can lead to an answer-only pass with tools disabled and `think:false`. Errors from that second pass propagate. The result includes passes, readings, combined usage/thinking, and inherited agent stop information. Thus “add stop to `LedgerResult`” is not a missing-field fix; proposed repeat/recovery counts are a separate enhancement. [Ledger.ts:202](src/core/ledgers/Ledger.ts#L202) [Ledger.ts:281](src/core/ledgers/Ledger.ts#L281) [Ledger.ts:298](src/core/ledgers/Ledger.ts#L298) [types.ts:284](src/core/ledgers/types.ts#L284)

The October 19 bounded probe reports the bare/prefixed contrast. This proves a linking defect in that case, not that fixing it improves the complete workload. ### Room, persistence, and replay

Ledger calibration makes two model requests with the same history/system, without and with tools. Their prompt counts estimate a character-to-token scale and fixed tool overhead. Planning reserves `predict`, applies the configured prompt share and observed scale drift, spends the tail share, and uses the residual for record lines. The gauge observes actual usage, the longest answer, and request growth; its recall-room calculation also accounts for replay policy. These are estimates and measured adjustments, not an exact tokenizer. [Ledger.ts:347](src/core/ledgers/Ledger.ts#L347) [Ledger.ts:621](src/core/ledgers/Ledger.ts#L621) [Gauge.ts:43](src/core/ledgers/Gauge.ts#L43)

Conversation snapshots retain ID, sections, live messages, and optional judgments; they do not serialize summarizer functions or all live configuration. `ConversationManager.open/save` explicitly load/save such snapshots. The memory store is a process-lifetime map without automatic eviction. This generic seam does **not** restore all Ledger-private state: Ledger has no public snapshot/restore option, and its gauge, registrations, request sets, and other bookkeeping require reconstruction by replay. [Conversation.ts:254](src/core/conversations/Conversation.ts#L254) [ConversationManager.ts:118](src/core/conversations/ConversationManager.ts#L118) [MemoryConversationStore.ts:42](src/core/conversations/stores/MemoryConversationStore.ts#L42) [types.ts:249](src/core/ledgers/types.ts#L249) [Records seed report][seed-records]

Thinking is separate from answer `content`. Replay policy is `none`, `turn` (after the last user message), or `all`; the agent applies it before provider dispatch. Requested thinking mode, stored reasoning text, replay policy, and an answer's factual correctness are therefore separate variables. ## 3. How Compaction works

Compaction changes the **view sent to the model**, while keeping folded originals in sections. `view()` renders framed assistant recaps followed by the live tail. `rehydrate` returns a section's originals; `search` searches original messages plus the tail. Neither automatically inserts the originals into the next prompt or gives a model a recall tool. [Conversation.ts:183](src/core/conversations/Conversation.ts#L183) [Conversation.ts:218](src/core/conversations/Conversation.ts#L218)

| Mode                 | Summary input and commit                                                                                                                           | Important limit                                                                                                                                                                                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary append      | Summarizes an eligible older live slice, strips its thinking, appends a section, and removes that slice from the live tail.                        | Earlier sections remain in the view, so prompt size can accumulate across folds. [Conversation.ts:268](src/core/conversations/Conversation.ts#L268)                                                                                                                                                 |
| Optional section cap | After the ordinary fold, excessive older sections can be merged by a second summary call over their summaries.                                     | The first fold is already committed when the cap merge starts; failure of the second call is not a rollback of the first. [Conversation.ts:316](src/core/conversations/Conversation.ts#L316)                                                                                                        |
| Opt-in rolling       | One call receives prior framed recap(s) plus the newly eligible slice; one replacement section retains all prior originals plus the new originals. | Earlier originals are preserved in storage but the summarizer sees their prior recap, so omitted facts can remain omitted. Rolling and a section cap are incompatible. [Conversation.ts:300](src/core/conversations/Conversation.ts#L300), [helpers.ts:172](src/core/conversations/helpers.ts#L172) |

The fold protects the newest user exchange and aligns the cut with complete exchanges/tool groups. Calls are serialized; aborts and conflicting mutation of the selected messages/sections prevent that fold's commit. “Keep 2” is a retained-tail setting constrained by those boundaries, not a promise to keep exactly two messages or two whole shifts. [Conversation.ts:193](src/core/conversations/Conversation.ts#L193) [Conversation.ts:275](src/core/conversations/Conversation.ts#L275) [Conversation.ts:302](src/core/conversations/Conversation.ts#L302)

Automatic compaction belongs to the agent's context-budget admission path. It measures the complete composed request, including instructions, tools, and options; when exhausted it permits one eligible compaction, recomposes/reselects, and measures again. A still-exhausted strict window throws `WINDOW`; a lenient path can dispatch. This is distinct from a native model overflow, a generated-output limit, or a study call/deadline limit. [Agent.ts:655](src/core/agents/Agent.ts#L655) [Agent.ts:686](src/core/agents/Agent.ts#L686) [Agent.ts:733](src/core/agents/Agent.ts#L733)

The default text estimate is `ceil(text.length / 4)` using JavaScript string length, plus framing, tool-call, image, advertised-tool, and schema estimates. It does not run a tokenizer or fully price a provider's chat template. A caller can supply a different budget consumer. [helpers.ts:237](src/core/agents/helpers.ts#L237) [helpers.ts:271](src/core/agents/helpers.ts#L271) [helpers.ts:340](src/core/agents/helpers.ts#L340)

The current Study consumer creates Records with `capacity = context − safety`, an explicit output reserve, prompt share 1 and tail share 0.35; Compaction uses a strict window of `context − output − safety`, `keep:2`, and optional rolling. Arrivals are deduplicated and source-tagged; lookups expose only the most recently released public version. The summary role uses the same agent model, thinking off, and a final user instruction. The Study summary implementation rejects blank text and invalid/missing usage. [StudyMemorySession.ts:118](studies/memory/StudyMemorySession.ts#L118) [StudyMemorySession.ts:146](studies/memory/StudyMemorySession.ts#L146) [StudyMemorySession.ts:194](studies/memory/StudyMemorySession.ts#L194) [StudyMemorySession.ts:263](studies/memory/StudyMemorySession.ts#L263) [StudyAgentSummary.ts:48](../study/src/server/agents/StudyAgentSummary.ts#L48)

## 4. What the sessions measured

### Measurement vocabulary

Study declares arms, ordered goals, repetitions, bounds, and a separate rubric. Each trial has fresh state, which persists across its goals. A seal establishes a complete terminal evidence population, which may include failure and unexecuted goals; it is not a quality certificate. Interrupted/unsealed evidence is a different status. Actual executed outcomes and later unexecuted cascades remain distinguishable. The framework reserves ceilings before dispatch and accounts conservatively for missing usage. [Study guide][study-guide]

The memory consumer's operational criterion requires a product without a goal failure **and no failure anywhere in the attempt**. Consequently, 21 completed products followed by a terminal fault can produce 96 unsuccessful operational judgments. That does not mean 96 generation failures. Semantic judgments remain independent. [helpers.ts:150](studies/memory/helpers.ts#L150) [Compaction qualification][compaction]

All main comparisons below have **one trajectory per arm/configuration**, not 24 or 96 independent replicated runs. Goals share evolving state. The old c1 rubric counts many facts/work/obligation atoms; the later Study rubric gives four holistic criteria per goal. Their percentages are not interchangeable. [results] [endurance]

### Gates, comparisons, and prospective cost limits

The ladder uses off, exact repeat, sham (a trailing space in the final user message), and on. It defines a noise allowance `N = 2 × max(|repeat − off|, |sham − off|)`; count improvement must exceed `max(2, ceil(.25 × baseline)) + N`, with metric-specific coverage and non-regression guards. Ordinary role speed target is ≥20%, sole-candidate whole-run ≥15%; S1 requires ≥25% prefill reduction and ≥.50 cached share. Semantic improvement target is ≥.10 targeted atom share beyond repeat/label uncertainty, with no critical regression. These are **prospective decision thresholds**, not confidence intervals or results. [ladder]

L1 normally needs two distinct failing targets and two clean guards at each affected early/late end. Baseline late-state surgery measures repair; prevention/cumulative treatments must start before first activation and carry actual generated history forward in earned segments. Replaying sealed later products as though a treatment generated them is disallowed. Early/late targets cannot be pooled to hide regression, and a correct tool argument alone does not establish a correct final product. [ladder]

| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Records / R**                      | Ledger selection of source-attributed record lines plus a tail, using judge filings and lookup identities. [Ledger.ts:484](src/core/ledgers/Ledger.ts#L484)                  |
| **Compaction / C**                   | Replacement of older model-visible messages by summaries while originals remain in conversation sections. [Conversation.ts:268](src/core/conversations/Conversation.ts#L268) |
| **Living aggregate**                 | Earlier maintained-summary treatment studied separately from the later rolling Compaction implementation. [results]                                                          |
| **Fold / recap / section**           | A fold summarizes an eligible slice; the recap is its text; a section holds that text and originals. [Conversation.ts:300](src/core/conversations/Conversation.ts#L300)      |
| **Gauge**                            | Estimated prompt price calibrated/adjusted with observed usage; not an exact tokenizer. [Gauge.ts:43](src/core/ledgers/Gauge.ts#L43)                                         |
| **Goal / shift / horizon**           | One requested product; a workload group of four products; the declared 96-goal population. [endurance]                                                                       |
| **Trial / series**                   | One fresh-state arm/scenario execution; the declared collection/schedule of trials. [study-guide]                                                                            |
| **Seed**                             | Either a model sampler value or reconstructed pre-goal state; these meanings are different and neither restores daemon cache automatically. [q4-off] [seed-compaction]       |
| **Tape**                             | Recorded judge HTTP exchanges used for exact-answer replay, with missing/unmatched requests handled explicitly. [seed-records] [ladder]                                      |
| **Custody / seal**                   | Immutable result/runtime identity and the terminal evidence integrity record; neither certifies semantic success. [study-guide]                                              |
| **Treatment / off / sham**           | An intentional behavior change; its unchanged control; a declared small perturbation used to calibrate effects. [ladder]                                                     |
| **Ladder / gate / promotion**        | Increasing experiment scales; their prerequisite checks; advancing only after the named mechanism, effect and guard evidence. [ladder]                                       |
| **Atom / holistic criterion**        | One specific factual/work obligation test versus a combined per-goal semantic judgment; denominators differ. [results] [measure]                                             |
| **Operational / semantic**           | Execution/usage/bounds correctness versus whether the product fulfills the task. [endurance]                                                                                 |
| **Prefill / decode / cached prompt** | Processing input; generating output; provider-reported reused prompt tokens. Cache counts alone are not time savings. [perf]                                                 |
| **Development / evaluation**         | Tuning/validation material versus the frozen evaluation population, with separate oracle-access rules. [ladder]                                                              |
