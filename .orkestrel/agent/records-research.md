# Records strategy evidence and bounded improvement plan

The measured cost has a narrow package seam: `Classifier.classify` resolves one question at a time, while the judge request can carry several questions for one state and `SystemOneJudge` enables that batch form. Group topic questions per message after category and quiet gates, preserve pair dependencies, and carry batch usage as request-level evidence. Treat arrival filing as latency movement with an explicit readiness barrier. Keep judgment cache identity exact. Measure retrieval and correction integrity before changing its data model.

## Evidence and limits

The c1 direction updated 2026-10-14 reports 2,626 one-token judge calls per 96-goal records run, labeled 27 per goal, 767,130 judge prompt tokens, and judge shares of 63/109 wall minutes at q4 and 56/100 at q2 (`.orkestrel/agent/direction.md:21-25`). These readings show a large request-path cost. They do not show how much comes from categories, topics, or correction pairs, and they do not predict the reduction from batching.

The same direction records a valid q2 thinking reading of 47% facts and 26% work for records across served products, 52 critical violations across 96 products, and a facts score decline from 68% to 36% across the horizon (`direction.md:13`). This supports a quality gate beside the cost gate. It does not attribute the violations to filing latency, batching, or a retrieval ranker. The q4 thinking run changes capacity settings and overflows, so its incomplete products stay outside semantic conclusions (`direction.md:9-11`).

`Classifier.classify` awaits category questions before topic questions, then awaits each `amends` result before conditionally asking `supersedes` (`src/core/ledgers/Classifier.ts:52-92`). Topic and category questions for a message use the same state string, `role: content`, and the same source ID (`Classifier.ts:227-268`). The pair question state contains both messages and ordered source IDs (`Classifier.ts:270-280`). `JudgeRequest` holds one state and many keyed questions (`src/core/types.ts:128-132`); `SystemOneJudge` enables batching (`src/core/providers/SystemOneJudge.ts:59-61`). `AgentJudge.ask` issues one call for a multi-question request when its batch option is true, or one call per question when false (`src/core/providers/AgentJudge.ts:104-135`).

The judgment cache already matches the JSON question text, rendered state text, ordered source IDs, and `judge.model` (`src/core/helpers.ts:371-391`; `src/core/conversations/JudgmentManager.ts:78-138`). The public `JudgeInterface` contract says `model` carries everything that changes an answer under a state (`src/core/types.ts:169-179`). The per-classifier failed-spec set also fingerprints the complete `JudgmentInput`, including its model (`Classifier.ts:316-350`). Preserve these exact comparisons. A cache identity gap exists only if a judge implementation reuses one model string across answer-changing configurations.

`Conversation.add` is synchronous and does not emit an arrival event; its emitter lists only compaction, collapse, and rehydration (`src/core/conversations/Conversation.ts:145-159`; `src/core/conversations/types.ts:183-197`). `Ledger.#select` runs classification before planning records (`src/core/ledgers/Ledger.ts:562-584`). Moving filing requires an awaitable host or package boundary. `JudgmentManager.resolve` has no in-flight coalescing; concurrent eager and request-path classification can duplicate an uncached judge call.

Batching also changes usage accounting. `buildJudgments` stores usage on a judgment only when its request had one question (`src/core/conversations/helpers.ts:22-42`), and `JudgmentManager.resolve` returns only judgment records (`JudgmentManager.ts:115-138`). A multi-question batch would lose aggregate usage from `ClassifierResult` unless the request-level usage travels separately. Do not smear a batch’s token count across individual records.

## Bounded candidates

### Priority: measured request-call reduction

Group pending topic questions by exact message state and resolve them together after the message category is known and the quiet check passes. Apply the same group to current-request topics only when `topic.requested` is not false. Keep category first, keep quiet skipping, keep request-topic filtering, and keep correction-pair questions in their present order. Pair states differ by source pair; `supersedes` depends on the `amends` threshold. Batching those phases together would spend work on a conditional question and would erase the existing gate.

Expect fewer transport requests only for judge implementations that batch inside `ask`; the generic `JudgeInterface` promises multi-question meaning, not one transport call. `SystemOneJudge` has the matching transport behavior. The question count may remain fixed. Prompt tokens may fall when the shared state is sent once, but measure them. A batch may also enlarge the failure domain: a malformed response can make a full group undecidable where serial calls retained earlier answers. Compare refusals, malformed replies, aborts, and partial completion explicitly.

Before accepting this change, return request-level aggregate usage to classifier reporting. Compare the serial and grouped strategy on the same judge model, exact question definitions, state bytes, and fresh judgment stores. Use fixed-transcript classification to compare each judgment distribution and refusal, then use the declared end-to-end scenario to compare facts, completed work, obligations, critical violations, coverage, corrections, and full product quality. Run each declared scenario’s full denominator; keep common-served and served-only summaries secondary. Record provider requests, logical questions, input/output tokens, judge wall time, total wall time, and host load per run.

Negative controls must include a quiet category that skips topics, `requested: false`, a correction below the correction threshold, an `amends` answer below threshold that produces no `supersedes` request, a partial correction that leaves unrelated lines intact, and an exact duplicate judgment that creates no extra call. A cancellation or malformed batch must preserve completed judgments and usage where available and must not turn missing questions into false labels. Keep repeat-lookup stops and answer-pass error propagation unchanged.

### Priority: preserve cache identity across strategy and judge changes

Keep exact state bytes, exact JSON question bytes with property order, ordered source IDs, and the behavior identity supplied by `judge.model`. Include every answer-changing judge setting in that identity. Check the System One endpoint and model revision against its stable configured identity before carrying judgments between conversations or runs; the persisted record stores `model`, while the endpoint is a separate option. If two answer-changing configurations can share one identity, namespace or extend the identity before reusing stored judgments. Do not add semantic-neighbor cache hits.

Use an identity matrix: exact repeat is a cache hit; one-byte changes to state or question, source-order changes, and a changed model/configuration identity each force a miss. Keep a cache-hit baseline and a miss baseline for every strategy arm. Give each arm a fresh judgment store so an earlier serial result cannot satisfy a later batched question. Retain the complete request-byte golden baseline and add any changed grouped bodies as a deliberate, reviewable baseline; do not rewrite the old bytes in place.

This candidate eliminates judge work only for an exact identity hit. It does not reduce the first classification of an incoming message. Report cache hits and misses separately from judge-request batching and from filing latency.

### Priority: move filing off the selection path only when overlap exists

Treat arrival filing as a scheduling design. An explicit `file` operation or an awaitable add hook can start classification when a message is added. Selection must wait for a stable conversation revision before reading categories, topics, or correction pairs. If another add/remove/clear changes that revision, either file the changed revision or select from the captured immutable snapshot. An emitter callback alone is not a barrier: the conversation emitter is synchronous and isolates listener failures.

Keep one in-flight filing per question identity, preserve message order for correction pairs, and make an abort or filing fault visible to selection. Define completion to include each question’s answered, refused, unknown, or failed state; selection must not read a partially completed batch. An unknown classification remains unknown. It does not become a favorable category to unblock the selection.

Measure total questions, calls, tokens, and total work alongside the judge wait in `respond`, time from arrival to filed readiness, time overlapped with independent tool/provider work, and time selection waits on the barrier. Moving work before a request can shorten the selection path while leaving total work unchanged. Overlap can hide time only when independent work exists. An immediate response after an arrival must wait when filing is unfinished; use a late correction during an in-flight batch and abort during filing as negative controls. If there is no independent interval, keep this candidate advisory because it moves latency without reducing it.

### Priority: measure retrieval and correction integrity before redesign

Preserve the existing correction contract. `Classifier.classification` records `amends` separately from `supersedes` and adds a supersedes relation to both maps only after its own threshold (`src/core/ledgers/Classifier.ts:175-224`). Record projection keeps source message IDs and sentence indices; full supersessions remove the old message from live records, while partial amendments mark only sentences that share an ID or number with the amendment as stale (`src/core/ledgers/helpers.ts:878-1034`; `src/core/ledgers/types.ts:361-430`).

Measure three separate stages: the filed source/correction state, the exact selected record lines presented before generation, and the generated answer. Include correct and incorrect correction links, current and stale facts, source attribution, wrong-entity exposure, unanswered or unknown classifications, obligations, critical violations, omissions, and refusal. Keep unscored items visible. This follows the 2026 preprint’s separation of stored-state validity, selected prompt contents, and final response; the paper finds that update assignment can matter more than ranking in its own keyed-memory setup. Its numerical results do not transfer to this ledger’s message-level relations. See [the 2026 memory-failure study](https://arxiv.org/abs/2610.10265).

Use false-correction and wrong-entity cases as negative controls: an unrelated record with overlapping topic text must stay live; a real partial correction must remove only its supported line; a full correction must not revive the old fact; and an unknown relation must stay unclassified. If these readings identify a specific projection or correction defect, isolate that defect in a later study. Do not add a graph database, embeddings, probabilistic keys, or destructive memory deletion without a measured error those mechanisms address.

External design evidence supports preserving evidence links and explicit invalidation history. Zep’s paper describes bi-temporal edges and episode-to-fact links, but says provenance links were not directly evaluated. Its 2026 first-party article describes source associations and invalidation lineage, without independent outcome evidence. Mem0’s paper describes ADD/UPDATE/DELETE/NOOP memory operations and asynchronous summary refresh, but its destructive deletion semantics do not meet this ledger’s retained-source contract. ARC caches a retrieval corpus by query patterns and embedding geometry; it is not an exact judgment-result cache. These are useful comparison points, not implementation prescriptions. See [the Zep paper](https://arxiv.org/abs/2501.13956), [Zep’s provenance design](https://www.getzep.com/blog/how-zep-tracks-provenance-in-agent-memory/), [the Mem0 paper](https://arxiv.org/abs/2504.19413), and [the ARC paper](https://arxiv.org/abs/2511.02919).

## Judge model comparison

If serial and batched requests produce different per-question answers, the strategy changes behavior identity. Keep those judgment stores separate or include strategy in the cache identity; do not let one arm’s decisions satisfy another arm’s questions.

Change strategy and judge model independently before a combined comparison. Run serial versus per-message topic batching with the same judge model and clean judgment stores. Run the baseline strategy with the candidate judge model and clean stores. Compare the combined strategy/model arm only after both isolated contrasts have readings. Hold scenarios, prompts, response budgets, retry policy, and host schedule fixed; give every arm a distinct result identity. Run paid or GPU-bound arms serially and record host load. Do not edit frozen manifests or prompts.

The Mem0 deletion comparison applies to its base pipeline. Its graph variant marks conflicting facts invalid; neither path specifies the ledger’s message-and-sentence provenance contract.

Report request count, question count, input/output tokens, latency, coverage, infrastructure outcomes, unknowns, corrections, obligations, facts/work scores, critical violations, and product acceptance as separate readings. Use the whole scenario denominator; report served-only comparisons over common goals as secondary. Preserve full captured request bytes for each arm, including any changed `questions` grouping, so wire changes are reviewable.

## What transfers

The high-confidence transfer is to batch same-state topic questions after their gates, preserve the classifier’s conditional phases, preserve the cache identity vector, and add request-level usage accounting before judging cost. The measured evidence also supports testing whether arrival filing can overlap independent work, with a strict readiness barrier.

The research does not establish that graph memory, semantic cache hits, entity embeddings, deletion of corrected facts, broader question batching, or a candidate judge model improves this ledger. Keep those mechanisms out of the proposed unit until a measured retrieval or classification defect names their target. The complete request-byte baseline, corrections, obligations, unknown classification, cancellation behavior, repeat-lookup guard, and answer-pass errors remain acceptance conditions.
