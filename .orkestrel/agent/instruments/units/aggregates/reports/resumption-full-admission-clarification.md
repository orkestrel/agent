## Version-tagged source findings

The following findings concern official source, not proven byte identity of the installed binaries. Each linked file is pinned to the named version or commit.

- **API fields.** `ChatRequest` and `GenerateRequest` expose separate top-level `truncate` and `shift` pointers. `ProcessModelResponse` exposes `context_length`, digest, and `runner`; `runner` describes a backend, not a process identifier. See [Ollama v0.40.2 API types](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/api/types.go), symbols `ChatRequest`, `GenerateRequest`, and `ProcessModelResponse`.
- **Native and rendered dispatch.** `ChatHandler` sends `req.Shift` to scheduling. `handleNativeChat` calls `prepareNativeChatRequest`; `truncateNativeChatMessages` returns `req.Messages` immediately when truncation is false. Native generation then calls `r.Chat`. Rendered chat calls `chatPrompt`, then `r.Completion` with the requested truncation setting. Raw generation also supplies `CompletionRequest.Truncate`. The default for omitted controls is true on these request paths. `optionsForPrompt` caps prompt options at `runner.ContextLength()`. `PsHandler` projects `loadedModels()` snapshots; its digest can be `ManifestDigest` rather than the selected child's digest. See [Ollama routes](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/server/routes.go), those symbols and `GenerateHandler`.
- **Rendered message removal.** `chatPrompt` enters its front-removal loop only when `truncate` is true. With false, it renders from the beginning. This is a context-removal control, not byte identity between input JSON and the model-specific template. See [Ollama prompt construction](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/server/prompt.go), `chatPrompt`.
- **Model clamp.** `NewLlamaServer` clamps requested `NumCtx` to positive GGUF training context before constructing the runner. `DoneReason.String` maps the length enum to `length`. See [Ollama runner interface](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/llm/server.go), `NewLlamaServer` and `DoneReason.String`.
- **Scheduler ownership.** `resolveContextShift` honors an explicit false. `load` copies it into `LlamaServerConfig.ContextShift`; `runnerRef.needsReload` detects a changed setting. `loadedModels` obtains context length from `r.llama.ContextLength()` under the runner lock. The snapshot exposes neither request association nor active slot occupancy. See [Ollama scheduler](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/server/sched.go), `resolveContextShift`, `load`, `needsReload`, and `loadedModels`.
- **Go adapter.** `completionPromptForRequest` bypasses token cropping when `Truncate` is false. `llamaServerChatRequest` converts every native message; `Chat` sends them to `/v1/chat/completions`. Shift is a launch attribute, not an inner request flag. `appendContextShiftArgs(false)` omits the enable flag; `SetupLlamaServerCommandEnv` inherits the environment. `ContextLength()` returns stored `options.NumCtx`; launch uses that value times parallelism for `-c`. `Completion` maps `stop_type=limit` to length; `Chat` maps `finish_reason=length` similarly. Their final counts come from timings; `promptEvalCount` adds cached and evaluated prompt tokens when a cache count exists. These facts do not make `/api/ps` direct slot telemetry. See [Ollama llama-server adapter](https://raw.githubusercontent.com/ollama/ollama/v0.40.2/llm/llama_server.go), the named symbols.
- **Runner limits.** `server_context_impl` rejects oversized input against `slot.n_ctx`. `process_token` stops with `STOP_TYPE_LIMIT` at context exhaustion when shifting is disabled. `pre_decode` discards cached context when shifting is enabled. Both paths can set `truncated=true`, so that flag alone does not distinguish history removal from stopping at capacity. `n_ctx_slot()` also considers per-slot and training caps. See [llama.cpp server context](https://raw.githubusercontent.com/ggml-org/llama.cpp/631109b34/tools/server/server-context.cpp), `process_token`, `pre_decode`, and `n_ctx_slot`.
- **Launch default and override.** `common_params.ctx_shift` defaults false, but the context-shift argument accepts the `LLAMA_ARG_CONTEXT_SHIFT` environment variable. Therefore omission of the enable flag is insufficient when inherited environment is unbound. See [llama.cpp parameters](https://raw.githubusercontent.com/ggml-org/llama.cpp/631109b34/common/common.h), `common_params`, and [llama.cpp argument processing](https://raw.githubusercontent.com/ggml-org/llama.cpp/631109b34/common/arg.cpp), the context-shift option registration.

## Minimal observable contract

Retain the first report's empirical bound `B`, requested window `W`, frozen qualification ceiling `C`, exact outgoing history, finite limits, and actual usage checks. Replace its proposed `allocation.runner` and `integrity.truncated=false` attestations with the following evidence requirements.

1. **Bind the deployment before qualification.** Hash a service-control receipt containing daemon and runner identities, model/backend selection, inspected source references, successful bounded controls, and the exclusive serial-client condition. Bind the nonsecret runner environment relevant to shifting and per-slot capacity. Verify `LLAMA_ARG_CONTEXT_SHIFT` is absent or false; do not infer the daemon's inherited environment from the interactive shell. If that state cannot be observed, require a controlled successor daemon launch in a separately authorized unit. A deployment or environment change invalidates the receipt.
2. **Disable removal explicitly.** Every covered generation body carries `truncate:false` and `shift:false`, including initial decisions, tool continuations, answer recovery, and calibration. Apply the decision policy identically across comparison arms and phases. Record other roles' control settings and account for their reloads; do not change judge or summarizer semantics merely to avoid reloads. Extending false to those roles is a separately recorded operational setting, not an inferred requirement of full-view history. Adding `shift:false` requires a successor source/configuration freeze and is not unchanged wire.
3. **Observe each completed call before the next service request.** In the existing fetch boundary, retain the raw request and complete response, then read and retain `/api/ps` before releasing the call to downstream work. Match an unambiguous model/backend entry through the frozen manifest/selected-child mapping, not a tag or an assumed equality between parent and child digests. Record `MatrixRequest.capacity: { window, evidence }`, where `window=A` is the snapshot's loaded configured context and `evidence` hashes the raw snapshot and timestamps. Require `A >= C`; never lower `C` after seeing a trajectory. Empty, ambiguous, stale, or changed observations leave qualification unresolved. Preserve failed-call evidence even when no model remains loaded.
4. **Qualify the complete observed trajectory.** Require complete outgoing chronological history at every decision boundary, successful completed responses, valid integer usage, unchanged reserve compliance, no error record, no length finish, and `prompt + completion < C`. Refuse explicit truncation evidence when available, but do not demand a success-response field the API does not expose. No answer score enters the decision. Keep `B > C` admissible for a finite empirical attempt; only the actual trajectory can qualify. Resource failure invalidates that trajectory, while unknown capacity and HTTP 500 remain outside answer quality and model-infeasibility claims.

The snapshot-to-call association is an inference under exclusive serial use: the successful call has completed, no intervening role can reload its model, and the snapshot is taken before another request proceeds. It is not a general concurrency guarantee or proof of a particular PID. The deployed receipt must demonstrate that this sequence reports the configured context of the serving model, including a role-driven context change. Failed exclusivity or ambiguous custody blocks qualification; do not compensate by inventing identifiers.

The observation remains honestly named **loaded configured context**. Before using it as `C`, validate its relation to actual per-sequence capacity for the deployment and frozen launch configuration. A bounded control's slot/context observation can establish that relation; it need not become per-request log attestation. Preserve each snapshot and the receipt so a reader can distinguish observed fields from this validated inference.
