# Compaction regression in v6: diagnosis

The drop from 6 to 3 passes comes from one goal fold, not from the `Identifiers:` line. In `ab-comp-tool` g01, the fold of seed 25-43 (19 messages) returned `No facts.` on both summarize calls (`calls[].completion` 4 and 4, label `summarize`). That fold held the ESC-2219 correction (seed 27), the MX-4486 rotation (seed 29), pro number FL-660412 (seed 36), and Luis's account LH-44870 (seed 40-43). The guard turned it into a bare line, so every later prompt pairs a stale but accurate sentence in the seed section ("ticket ESC-2291 created", "manager code MX-4471") with a list of ids that has no status. The identifier-loss check did not cause a failure and did not rescue a pass. It did carry dead ids into every prompt, and in one fold its retry replaced a real summary.

## Answers

1. The check is neutral on score and harmful in content. A line carried a dead id (ESC-2291 or MX-4471) into the agent prompts of 10 of 10 goals in `ab-comp-tool` and 6 of 10 in `ab-comp-terminal` (g05-g10). In every `ab-comp-tool` goal, a prose sentence in S1 carried the same dead ids too, so no failure rests on the line alone. S3, a misattributed line, sat in 6 `ab-comp-tool` prompts (g04-g09) and reached one reply, g05's "Luis Whitcombe (account LH-20418)" (unscored). No pass in the 3 runs rests on an id found only in a line: terminal g03's PW-5521-9930 also came from its LH-77302 lookup. The retry also did harm: in terminal g06 (`guard.calls[0]`: missing 5, lost 11), the retry replaced a 229-token summary with `No facts.`.
2. The check explains none of the drop. Comparing v4 with `ab-comp-tool` goal by goal (`success`), the tool arm lost g02 and g04 to the g01 `No facts.` fold, lost g08 and g10 to the model on correct prompts, and gained g09 because its S1 kept "gift note 'Happy 40th, Aiko'" where v4 had "logs gift note LH-81660 for Aiko". g05, g06, and g07 failed in both runs. The summaries therefore account for 2 of the 4 lost passes and the 1 gain; the model accounts for the other 2 losses.
3. Longer replies did not help: terminal goal folds lost reply context too. Its g03 reply "Manager Code: MX-4471 / Current: MX-4486" ended up in the bare line of the g05 fold (`Identifiers: LH-77302, LH-20418, PW-5521-9930, MX-4471, MX-4486`). The terminal arm did better for 3 reasons. First, its smaller `toolEstimate` (266 compared with 335) moved the seed fold boundary to 29, so the correction at seed 27 shared a fold with the value it corrects ("ESC-2219 (replaced previous ESC-2291)"), as in v2's single 43-message fold ("MX-4471 (rotated to MX-4486)"). Second, its one large goal fold (g03, 21 messages) returned prose. Third, it made 15 tool calls including 3 `search_history` calls (g04, g09, g10), against 3 lookups and no search in the tool arm (`tools`). Seed 40, the only sentence that ties Luis to LH-44870, was folded before g02 in the tool arm and stayed live through g02 in the terminal arm. The audit of the tool descriptions owns why the tool estimates differ.
4. Keep each id with the sentence that gives its status, built extractively, because it rests only on the input text and on message order. When a summary loses an id, append the last input sentence that carries it, verbatim, in place of the bare id. This gives seed 27 "the ticket is ESC-2219, not ESC-2291", seed 30 "Switched to approval code MX-4486 and retired MX-4471.", seed 42 "Order LH-79215 for account LH-44870 (Luis Ferreira)", and seed 37 for FL-660412. v4 g04 shows that a later sentence of this form beats S1's stale ESC-2291. The fix has 2 more parts. First, treat `No facts.` as a failed summary whenever the input holds an identifier. Second, keep the retry only when it loses fewer ids than the first summary, which would have saved terminal g06. Two other options were ruled out. Writing "ESC-2291 (replaced by ESC-2219)" requires the harness to know which value supersedes which; only the summarizer can know that without reading scenario facts, so it is not fair. Dropping the line leaves the scores in these runs unchanged and removes ESC-2219, MX-4486, FL-660412, and LH-44870 from every `ab-comp-tool` prompt after g01. The extractive line costs prompt tokens, and nobody has measured that cost. Check the fix with a `--probe-guard` case whose stub summarizer returns `No facts.`, then rerun both `ab-comp` arms.

## Method

Scratchpad scripts read the 3 `compaction.jsonl` files and `scenario.json`. Seed indices come from matching g01's first agent call against `seedFolds[].messages`. The record holds no summarizer output text, so 4-token completions are read as `No facts.`: the guard writes a bare line only when the summary is empty or exactly `No facts.` (`bench.mjs` `guardSummary`).
