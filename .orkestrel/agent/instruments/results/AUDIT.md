# Harness and agent wiring audit (2026-10-08)

This audit covers the v2 runs under `results/v2/` (none-words, c-tuned-s3, c-generic-s3, selection-tuned, both-tuned, and selection-tuned-oom) against `bench.mjs`, the package source in `/home/user/agent/src/core`, and the judge source in `/home/user/ollama/src/core`. The directory `results/dump/` exists and holds no files, so no claim in this audit rests on a captured request or response body. Run citations take the form `run:goal:field`, where the goal number is also the jsonl line number.

## Answer

The package loop runs as coded: every recorded agent call ended on `done_reason` "stop" within 1 or 2 of its 8 turns, the view grows by the expected count per goal (selection-tuned.log:18-27), and inside the package each tool message carries the id of the call it answers (Agent.ts:529-554). The disconnects sit at the seams, where whole exchanges reach the model broken: the wire drops every tool-call id and tool name (bench.mjs:192-200), selection keeps a reply without the request it answered (selection-tuned:g04:selections[0].judgments), and compaction folds a lookup call away from its result (c-tuned-s3:g07 and c-generic-s3:g07, by count arithmetic). The harness contract and the loop contract differ: the system prompt and the scorer count only `send_reply`, the loop accepts a prose turn as the final answer (Agent.ts:567-572), and the seed itself shows three lookups answered in prose with no `send_reply` (scenario.json seed 14-17, 35-37, 41-43). Neither model returns the same output for prompts the records show as identical across runner loads (judge p up to 0.042 apart, agent completion 39 against 35 tokens), so a one-goal difference between arms is not a finding until repeats exist. The summarizer receives no date, the selection drops the date anchor, the scorer passes 3 wrong replies and fails 1 right one, and every claim about how the qwen3.5 template renders these messages stays unverified until the wire dump exists.

## The eight graded observations

Each paragraph that follows explains one observation from the setting and cites the finding behind it.

### 1. A correct answer in plain text with no `send_reply`

The graded files hold 4 such goals, not 3: none-words g02 and selection-tuned g01, g02, and g08 (GRADES-1.md:17); both-tuned adds g01, g02, g06, and g08, and selection-tuned-oom adds g01 and g02. Every agent call on the 4 graded goals ended with `reason` "stop", none truncated or overflowed, and each goal used 1 or 2 of its 8 turns (selection-tuned:g01:calls[0], g02:calls[0-1], g08:calls[0-1]; none-words:g02:calls[0-1]), so neither the turn limit nor the context cut the answer short. The tools were offered by the code path: no scope is set (bench.mjs:724-740), `filterAllowList` returns every definition for an undefined allow list (helpers.ts:39), and the body carries the tools array when it is non-empty (bench.mjs:288-299); the bodies themselves are unverified. The loop takes any turn without a tool call as the final answer (Agent.ts:567-572), and the model has precedent for that turn: the seed answers each of its 3 lookups in prose and never calls `send_reply` (scenario.json seed 14-17, 35-37, 41-43), and in selection-tuned the g01 prose answer stays in the view before g02 (view 49 to 50, selection-tuned.log:18). Both compaction arms fold seed 0-42 into a recap before g01 and replied on all 20 goals (c-tuned-s3 and c-generic-s3 lines 1-10 `replied`), which fits the seed precedent as the cause; that link is inference. Selection-tuned g01 called no lookup at all. Finding A5 closes the scoring side; finding A3 is a possible contributor, because a lookup result reaches the template without its tool name.

### 2. The g04 resend in the selection run

The judge decided each g04 candidate alone against the g04 request: it dropped the g03 request (`ca226b26`, p 0.0814) and the g02 answer (p 0.0943), and kept the g03 `send_reply` call (p 0.1944) and its "sent" result (p 0.1876) as undecided (selection-tuned:g04:selections[0].judgments). The group rule played no part, because each member survived on its own probability, and a user request is never part of a group (helpers.ts:155-158). The model therefore read a `send_reply(note)` call, a "sent" result, and the g04 request, with no g03 request before them, and its one call resent the g03 note word for word (selection-tuned:g04:tools, `missing` ["esc-2219"]). Finding A1 closes this; finding A3 keeps the orphaned pair from reading as the answer to whatever user message precedes it. The pairing of the non-seed ids to g01-g03 messages is inference from newest-first order and counts, and the g04 agent request body would confirm it.

### 3. The dropped date line and the "Friday" replies

The date anchor, seed 0 ("Morning, it's Thursday 2026-10-08"), scored p 0.005-0.040 in g02 and g06-g10 and was dropped there (selection-tuned:g02,g06-g10:droppedSeed; both-tuned shows the same pattern). The "needed" criterion asks whether one message is needed for one request (helpers.ts:20-22), and a date line has no lookup relevance taken alone. Seed 8 ("off tomorrow, Friday 2026-10-09") was kept in g07 (p 0.942) and g10 (p 0.191, undecided), so the model saw "tomorrow, Friday" with no today to anchor it and wrote "today, Friday, October 9th" (selection-tuned:g07:tools and g10:tools). Finding C1 closes this. The compaction arms reached the same error by another path, covered in observation 7.

### 4. Different message sets from the same selection settings

Both causes the setting names are present, and they chain. At g02 turn 2 both runs sent prompts that match on every recorded field (prompt 1166 tokens, equal `droppedSeed`, same lookup), and the agent returned 39 tokens in selection-tuned and 35 in both-tuned, so the g02 answer text differs (selection-tuned:g02:content against both-tuned:g02:content). That answer is a g04 candidate, and its probability landed on either side of the 0.1 cut: 0.0943 dropped against 0.1023 kept, which is the 16 against 17 split (selection-tuned:g04:selects[0] and both-tuned:g04:selects[0]). Separately, the judge returned different probabilities for states whose prompt totals match exactly: g01 seed 0 at 0.6564 against 0.6140, and seeds 6-14 in g02 and g04-g06 (finding A4); none of those crossed a cut in g04, while g07 seed 10 did (0.1184 against 0.0831). Byte identity of the prompts is unverified, because no body hash is recorded (finding D5), and the cause of the drift is unverified; the both-tuned call that took 2970 ms against 18861 ms is consistent with a prefix-cache hit, which is inference.

### 5. Echoed prompt decorations in the bench3 harness copy

The bench3 harness rewrites message content before it reaches the model: it prefixes `[mN] ` and appends `[amended by mK]` (bench3/bench.mjs:1329) and prefixes the request with its handle (bench3/bench.mjs:2055). The model sees those marks as part of user and assistant turns and continues the format, and bench3/README.md:303 records a g01 smoke answer that began `[m48] `. The v2 runs did not carry this, because bench.mjs sends stored content unchanged (bench.mjs:192-200) and puts the bounded markers only in the judge prompt (bench.mjs:53, 380-404). Finding A7 closes this in bench3.

### 6. `search_history` never called

No goal in the 5 run files called `search_history` (`tools` on every line), and 6 of the 40 graded goals never reached the model, because none-words g05-g10 were refused with HTTP 400 for 3112-3301 prompt tokens over `num_ctx` 3072 (none-words:g05-g10:error; finding D1). In selection-tuned the facts of g09 and g10 (seeds 11 and 24) were in view (`inPrompt` true, lines 9 and 10), so no search was needed there; the facts were out of view on g05 and g06 (`inPrompt` false), where the model replied without searching. The model has no signal that a fact is missing: selection leaves no trace of a dropped message (AgentContext.ts:232-246), a recap reads as a complete account, and the seed holds no example of a search. The system prompt's condition, "when a fact you need is not in view", is therefore not observable from the prompt (finding A8). Whether the tools array in each agent body lists `search_history` with its description is settled by code (finding A5 evidence) and unverified on the wire.

### 7. Summaries that lost identifiers and turned "off tomorrow, Friday" into a deadline

The tuned first fold summarized seed 0-42 in one call of 1749 prompt and 239 completion tokens and dropped PW-5521-9930, FL-660412, Riverside, Freightline, Parcelway, and seed 0's date (c-tuned-s3:g01:calls[0], sectionsHeld[0]); c-tuned-s3 g07 then missed `fl-660412` (finding C4). The summarizer received no date and no system prompt (finding A6), and the tuned instruction asks to keep date tokens without their meaning (finding C2), so "off tomorrow, Friday" became "handles depot releases until Friday, Oct 9", and the generic summary kept Thursday but wrote "off until Friday"; both g07 replies gave a Friday deadline. The g07 folds in both runs cut between g06's `lookup_order` call and its result (finding A2), and the generic section built from that cut ends in "Next Steps: Retrieve the order details for LH-81660", which preceded the g08 lookup of the wrong account LH-52307; that cause is inference. The generic cap merge at g08 summarized two summaries and lost the gift note, Tomasz, FL-660412, ext 4127, and MX-4486, after which g09 invented gift wording and g10 gave "555-0192" (c-generic-s3:g08:sectionsHeld[0], g09:missing, g10:missing; finding C3). The compaction tracer's claim that the g01 fold split `call_4` from its result is wrong: seed 41 is the call and seed 42 its result (scenario.json seed), so the fold of seed 0-42 kept them together and left the prose answer at seed 43 live.

### 8. The g04 scorer failure for "corrected from ESC-2291"

The scorer tests forbidden values as case-folded substrings with no negation or context (bench.mjs:783-793), and g04 forbids "esc-2291" as a plain value (scenario.json g04). The reply "ESC-2219 (corrected from ESC-2291)" names the right ticket and marks the wrong one as corrected, and the substring test failed it (selection-tuned-oom:g04:violations). GRADES-1.md:18 reports no false fails because the oom file is not among the graded files (GRADES-1.md:1). Finding D2 closes this, and finding D3 closes the opposite error, where 3 wrong replies pass.

The dump writer stores each exchange as `NNN-gXX-LABEL-request.json` (line 1 the URL and method, line 2 the body) and `NNN-gXX-LABEL-response-STATUS.txt`, where `LABEL` is `agent`, `summarize`, or `judge` and `gXX` is the goal tag (bench.mjs:128-136, 250, 347, 801). - [ ] Every agent request body has a `tools` array with `lookup_order`, `lookup_customer`, `search_history`, and `send_reply`, including the turns that ended in prose (A5, observation 6).
- [ ] Assistant `tool_calls` entries carry no `id`, and tool messages carry no `tool_name` or `tool_call_id` (A3).
- [ ] A lookup turn's response stream shows whether Ollama 0.40.0 returns `tool_calls[].id`; if it does not, the harness minted the id (bench.mjs:224).

- [ ] In the selection g04 agent body, the g03 `send_reply` call and its "sent" result sit directly before the g04 request with no g03 request (A1), and the message order matches the newest-first id pairing in observation 2.
- [ ] Each judge body has `raw` true, `options` with `num_ctx` 4096, `num_predict` 1, `temperature` 1, and no `seed`, and a prompt with no message ids (judge trace).
- [ ] Each judge response's first-position `top_logprobs` lists both `No` and `Yes`; record the summed No and Yes mass against the rest.
- [ ] A dumped g01 judge question for seed 0 gives a p equal to 0.6564 or 0.6140, or a third value; a third value confirms A4 on a third load.
- [ ] Each summarize body holds the folded messages and one user instruction, with no system message and no tools (A6).

## Fix plan

The fixes that follow are in the order to land them; steps 1-3 change no model input and need no rerun, and steps 4-8 change prompts and land together before one rerun of every arm.

1. Rescore the recorded jsonl with the fixed scorer (A5 scoring, D1 marking, D2, D3, D4). No model call is needed. Expected changes: selection-tuned-oom g04 passes; c-generic-s3 g07, c-tuned-s3 g08, and selection-tuned g10 fail; the 4 graded prose answers count as answers with a reply skip each; none-words g05-g10 read as overflow.
2. Add the instrumentation (D5, D6, D8): body hash, tool count, ids, per-judge-call time and prompt, decision margin, and per-turn content. This changes only later runs.
3. Measure repeatability (A4): send one judge request and one agent request twice warm and twice after a reload. If outputs differ, every arm needs repeated runs and a goal-level difference between arms needs to exceed the spread before it counts.
4. Send `tool_name` on tool messages (A3). This changes every prompt after the first tool message, so it invalidates all 5 v2 arms.
5. Keep exchanges whole in selection and exclude seed 0 from the candidates (A1, C1). This invalidates selection-tuned and both-tuned.
6. Fix compaction: the fold boundary (A2), the post-abort `#trim` (B1), the summarizer system message with the date (A6), the fact-only instruction (C2), merging from originals (C3), and the first fold size (C4). This invalidates c-tuned-s3, c-generic-s3, and both-tuned.
7. Keep a failed judge subject undecided and recognize the judge abort class (B2, B3). This changes only goals with judge faults; selection-tuned-oom is replaced by the step 5 rerun.
8. State in the system prompt that messages can be omitted and when to search (A8). This changes every prompt and invalidates all 5 arms.
9. Rerun none, c-tuned-s3, c-generic-s3, selection-tuned, and both-tuned with the dump on, the repeat count from step 3, and none at a `num_ctx` that holds its g10 prompt; then grade the reruns. Separately, apply A7 in bench3 and rerun its smoke.

## Before thinking mode and a 4B model

The following conditions must hold before either change is tried, because each change otherwise lands on a measurement that cannot separate the model from the harness.

- Steps 1-9 of the fix plan are landed, and the reruns are graded; the graded 2B reruns are the reference, not the v2 numbers.
- The wire dump checklist passes on one goal per mode, with tool names on the wire and no orphaned call, result, or reply in any agent body.
- The repeatability spread from step 3 is known, and the repeat count covers it.
- A flag scopes `think` to the agent provider only: bench.mjs:283 sends `think: false` on every provider body, including the summarizer, and the judge prompt pins an empty think block (ollama helpers.ts:91). Thinking text is read (bench.mjs:308) and not stored in the conversation (Agent.ts:529-533, 568); the dump must confirm that the next request carries none.
- Thinking tokens count in `eval_count` and against `num_ctx`: the largest recorded agent prompt is 2363 tokens of 3072 (c-tuned-s3:g07:calls[0]), so the run must record thinking length per call and count `truncated` before any quality claim.
- For a 4B model, the judge and the agent must fit beside each other or the swap time must be recorded per call: the daemon runs with `OLLAMA_MAX_LOADED_MODELS=1` (runnerC3.sh:16), and Mica at `num_ctx` 4096 beside qwen reached about 10.9 GB and was stopped twice by the memory cgroup (bench3/README.md:302).
- The window estimate must be recalibrated against the 4B model's prompt counts from a dump, because the 1.46-1.96 ratio in D7 was measured on the 2B.
